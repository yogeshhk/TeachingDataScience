\begin{frame}\frametitle{After Learning Machine Learning}

\begin{itemize}
\item Once you create your machine learning algorithm, that research part is done.
\item Then you really start the bulk of the work.
\item How will the results of your model be delivered to the end user?
\item That's called ``putting it in Production'' or ``Deployment''
\end{itemize}

\begin{block}{Intuition}
Training a model is like designing a product; deployment is manufacturing and shipping it.
Most of the real engineering effort, and most of what can go wrong, happens after the
algorithm itself is done.
\end{block}
\end{frame}

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\begin{frame}\frametitle{What's Needed}

\begin{itemize}
\item You'll need powerful hardware to run your model at a reasonable speed.
\item That means running your machine learning API on the cloud.
\item You run it on a cloud server and send the results back to the user!
\item You automate your system pipeline and have it ready to automatically scale based on your user traffic!
\item Cloud computing is the workhorse behind the real-world machine learning applications.
\end{itemize}
\end{frame}

\begin{frame}\frametitle{Cloud Players}
\begin{itemize}
\item AWS: most popular, gives you the most control and customization.
\item Azure: offers ease of use at the expense of a bit of control and customization.
\item GCP: somewhere in the middle of the two, with some abstraction but not too much.
\end{itemize}
\end{frame}

\begin{frame}\frametitle{Building Blocks of a Cloud Deployment}
Every cloud provider offers the same kinds of building blocks, under different names:
\begin{center}
\small\renewcommand{\arraystretch}{1.35}
\begin{tabular}{>{\raggedright\arraybackslash}p{0.25\linewidth}>{\raggedright\arraybackslash}p{0.5\linewidth}l}
\hline
\textbf{Building block} & \textbf{Job} & \textbf{AWS example} \\
\hline
Virtual servers & run the model and its API; scale with demand & EC2 \\
Serverless functions & run code only when an event occurs & Lambda \\
Object storage & store data, models and logs cheaply & S3 \\
Managed database & keep structured data and model results & RDS \\
Automated deployment & ship new code and models on every commit & CodeDeploy \\
Monitoring and logs & watch the running system continuously & CloudWatch \\
Message queue & keep jobs organized and in order & SQS \\
API management & build, deploy and manage APIs at scale & API Gateway \\
Managed ML platform & build, train and deploy models with a high-level interface & SageMaker \\
\hline
\end{tabular}
\end{center}
\end{frame}

\begin{frame}[fragile]\frametitle{Quick Check: Production and Deployment}
\begin{block}{Think About It}
A company wants to deploy a fraud-detection model that flags suspicious transactions in
real time as customers make purchases. Would an event-triggered serverless function or a
continuously-running server be the better architectural fit, and why?
\end{block}
\end{frame}

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\begin{frame}[fragile]\frametitle{Quick Check: Production and Deployment}
\begin{block}{Answer}
A serverless function fits well here: fraud-checking is a short-lived, event-driven task (react to each
transaction as it happens) rather than something needing a server running and warmed up
24/7, so an event trigger avoids paying for idle capacity and scales automatically with
transaction volume. A continuously-running server suits models that need to stay loaded in memory and serve requests
continuously at low latency, such as a recommendation engine backing every page load. Serverless has limits, though: a large model or a strict latency target can favor an always-on server, because a cold start adds delay.
\end{block}
\end{frame}
